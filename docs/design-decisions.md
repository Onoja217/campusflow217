# CampusFlow design decisions and code contracts

This document describes the implementation currently on `main`. It is intended to help contributors reason about the code and test it without relying on undocumented assumptions.

## 1. Ticket model and collection

The canonical record is the frozen `Ticket` dataclass in `campusflow/tickets.py`. It contains exactly these fields:

| Field | Meaning |
| --- | --- |
| `id` | String identifier such as `T001` |
| `title` | Trimmed, non-blank summary |
| `category` | `Network`, `Hardware`, `Software`, or `Other` |
| `urgency` | `low`, `medium`, or `high` |
| `affected_users` | Positive integer (booleans are rejected) |
| `priority` | Calculated `low`, `medium`, `high`, or `critical` |
| `status` | `open`, `in_progress`, or `resolved` |
| `assigned_to` | A non-blank assignee string or `None` |

The application keeps tickets in a Python list in memory. Business helpers accept an iterable or mutable sequence, depending on the operation; several helpers also accept mapping-shaped ticket records for compatibility. The normal persisted and CLI representation is `Ticket`.

IDs are generated by `next_ticket_id()` from the highest valid numeric suffix currently in the collection, not simply from the last item. The next ID is formatted with at least three digits (for example, `T001`, `T012`, `T1000`). Persistence rejects duplicate IDs.

## 2. Validation and workflow errors

Validation and business rules are centralized in `campusflow/tickets.py`, so callers such as the CLI and browser interface can reuse them.

- `validate_title()` trims a title and rejects non-string or blank values.
- `normalize_category()` trims and matches supported category names case-insensitively, returning the canonical spelling.
- `normalize_urgency()` trims and matches supported urgency values case-insensitively, returning lowercase.
- `validate_affected_users()` requires a positive integer and rejects booleans, strings, and floats. `parse_affected_users_input()` parses CLI text without truncating decimal or other non-integer input.
- `calculate_priority()` applies the documented priority precedence: high urgency with at least 10 affected users is critical; otherwise high urgency or at least 10 users is high; otherwise medium urgency or at least 3 users is medium; otherwise low.
- `assign_ticket()`, `change_ticket_status()`, and `reopen_ticket()` raise `TicketValidationError` when an ID is missing, an input is invalid, or a workflow transition is disallowed.

Allowed normal transitions are `open → in_progress → resolved`. A ticket must be assigned before it can move from `open` to `in_progress`. Resolved tickets cannot be modified through normal assignment/status actions; `reopen_ticket()` is the explicit operation to return a resolved ticket to `open`.

Business helpers do not print user-facing messages. The CLI catches `TicketValidationError` and prints an `Error:` message. A missing ticket lookup is represented by `None`, rather than an exception.

## 3. Return-value contracts

| Function / module | Success result | Failure behavior / notes |
| --- | --- | --- |
| `create_ticket()` | Returns the created `Ticket` and appends it to the supplied mutable sequence | Raises `TicketValidationError`; validates fields before appending |
| `get_ticket_by_id()` | Matching record | Returns `None` for a blank/non-string or unmatched ID |
| `list_tickets()` | New list in collection order | Does not mutate the source collection |
| `assign_ticket()` | Updated ticket record | Raises `TicketValidationError` for missing ID, blank assignee, resolved ticket, or read-only record |
| `change_ticket_status()` / `reopen_ticket()` | Updated ticket record | Raises `TicketValidationError` for unsupported transitions or records |
| `format_ticket_list()` / `format_ticket_details()` | Formatted string | Empty list formatting returns `No tickets found.` |
| `prioritized_tickets()` | New sorted list of unresolved records | Filters out resolved tickets; does not mutate input |
| `build_ticket_report()` | Dictionary containing `total`, `by_status`, and `by_priority` counts | Reads the supplied iterable once and does not mutate it |
| `load_tickets()` | List of validated `Ticket` records | Missing file returns an empty list; unsafe or invalid data raises `TicketPersistenceError` |
| `save_tickets()` | Returns `None` after a successful save | Raises `TicketPersistenceError` when records cannot be validated or written |
| CLI mutation handlers | Print confirmation only after persistence succeeds | On save failure, `_save_or_rollback()` restores the in-memory list and prints a persistence error |

These contracts distinguish validation/business errors from persistence errors. The interfaces are synchronous and use the Python standard library; no third-party runtime package is required.

## 4. JSON persistence and restart behavior

Persistence is isolated in `campusflow/persistence.py`.

- Default path: `data/tickets.json`, relative to the process working directory. Run CampusFlow from the repository root for the documented default location.
- The file contains a JSON array; each item must have exactly the eight ticket fields listed above.
- Loading validates field shape and values and rejects duplicate IDs. Missing files are treated as a new empty workspace. Malformed JSON, invalid records, and other read failures raise `TicketPersistenceError`; invalid existing data is not silently replaced.
- Saving validates records, creates the parent directory if needed, writes UTF-8 JSON to a temporary file in the same directory, flushes and syncs it, then uses atomic replacement. Temporary files are cleaned up after a failed replacement when possible.
- The CLI loads records at startup and saves after successful mutations. The browser dashboard uses the same default JSON file and business rules. Avoid running multiple writers against the same file simultaneously; this application does not provide cross-process write coordination.

The CLI rolls back its in-memory collection if a save fails. The persistence layer itself raises an exception instead of printing messages or deciding how a user interface should recover.

## 5. Module boundaries and tests

| Module | Responsibility |
| --- | --- |
| `campusflow/tickets.py` | Ticket model, input validation, priority calculation, IDs, lookup, assignment, status workflow, and formatting |
| `campusflow/persistence.py` | JSON serialization, record validation, safe load/save behavior |
| `campusflow/priority_queue.py` | Filtering unresolved tickets and ordering by priority then numeric ticket ID |
| `campusflow/reports.py` | Workload totals by supported status and priority |
| `campusflow/cli.py` | Interactive prompts, user-facing messages, menu routing, persistence orchestration and rollback |
| `campusflow/web.py` | Local browser dashboard and HTTP interface, reusing ticket rules and JSON persistence |
| `tests/` | Automated checks for business rules, CLI, persistence, queue, reports, and browser/CLI persistence smoke behavior |

Tests use the standard-library `unittest` framework. From the repository root, run the full suite:

```bash
python3 -m unittest discover -s tests -v
```

Persistence tests should use temporary directories and files rather than the default runtime data file.
